ADAPTING JPEG QUALITY TO THE UPLINK, LIKE A VIDEO CALL DOES
============================================================

GOAL
----
Keep the number of frames analyzed per second (fps) steady even when
the uplink (how fast your device can send data OUT to the internet)
gets worse mid-session -- instead of always sending the same picture
quality no matter what the connection is doing right now.

Status: implemented and deployed. LiveCameraPlayer.tsx (the logic) and
LatencyHud.tsx (the on-screen numbers). This file is the plain-English
version of what the code does, kept in sync with it.


THE ANALOGY THAT FITS, AND THE ONE THAT DOESN'T
------------------------------------------------
Two well-known approaches solve "pick quality dynamically." Only one
fits us.

1. YouTube-style
   Picks quality based on how many seconds of video are already
   pre-loaded and waiting (this pre-loaded video is called a
   "buffer"). The whole idea only works because the player is
   allowed to sit a few seconds behind live and wait.
   WRONG FIT FOR US -- we never want to wait. We want this exact
   frame's result as fast as possible, not a few seconds of
   lookahead.

2. Video-call-style (the method WebRTC uses, called
   "Google Congestion Control", GCC for short)
   No waiting allowed, the connection quality changes mid-call, and
   it has to decide what to send RIGHT NOW, this instant. This is
   our actual problem shape.


WHAT GCC DOES, IN PLAIN WORDS
-------------------------------
It watches a warning sign and reacts when it looks worse:

  - Is data taking LONGER to arrive than it used to?
    (This is "delay-based" detection -- an early warning that a
    queue is starting to build up, before anything has actually
    gone wrong yet. Our recv_ms, the server's own measurement of how
    long it waited to receive one picture, is exactly this number.)

GCC also has a second, separate warning sign -- actual data loss.
We don't have an equivalent, and that's fine, not a gap: we send
over a WebSocket, which runs on top of TCP. TCP's whole job is to
guarantee nothing is ever silently lost -- if a piece goes missing,
it gets automatically re-sent before our code ever sees anything
wrong. So on our transport, loss doesn't show up as missing data, it
shows up as extra delay (the resend takes time) -- which recv_ms
already captures. One detector covers both cases for us.

(This is also why we can't see individual network packets the way
GCC does -- TCP hides them on purpose. It bundles everything and
only hands our code the complete picture once it has fully arrived.)

GCC adjusts using two modes, not one constant step size:

  - "Slow start": while far from the limit, jump FAST -- you clearly
    have room, so there's nothing to be cautious about yet.
  - "Congestion avoidance": once close to the limit, creep up slowly,
    one small step at a time, and drop FAST the moment trouble shows.

In short: big steps when there's clearly room, small careful steps
near the edge, fast drops always.


MAPPED ONTO WHAT WE ALREADY MEASURE
-------------------------------------
We don't have per-packet data like GCC does -- we have one number per
frame. That's enough. Here's the translation:

  "Is it taking longer than usual?"
    -> recv_ms, compared each frame against a budget worked out from
       the fps floor you set (see FORMULA below).

  "Is there a lot of room, a little room, or none?"
    -> the gap between recv_ms and that budget. A big gap is treated
       like GCC's slow-start (jump to the ceiling); a small gap gets
       the cautious small step.

  "How do I change quality without overreacting to one noisy frame?"
    -> a rolling window of the last 15 frames' pass/fail, not a
       strict streak. See "WHY A WINDOW, NOT A STREAK" below.


THE FORMULA, PER PICTURE SENT
--------------------------------
  frame_budget_ms   = 1000 / target_fps
                       -- target_fps is the floor you set on the page
                          (default 10, a slider, your choice -- NOT a
                          speed cap. Running faster than this is fine
                          and expected; it's the minimum being
                          protected, not a target to match exactly)

  available_wire_ms = frame_budget_ms - resize_ms - server_ms
                       -- what's left for the network after resizing
                          the picture and running the model

  this picture is "good" if recv_ms <= available_wire_ms

  if NOT good:
      quality drops immediately (big multiplicative step down)

  if good:
      record it in a 15-picture rolling window
      if at least 80% of that window was "good":
          if recv_ms is under HALF of available_wire_ms (lots of room)
              -> jump quality straight to the ceiling (slow-start)
          else
              -> small step up (the cautious climb)


WHY A WINDOW, NOT A STREAK
-----------------------------
The first version required 10 good pictures IN A ROW, zero misses,
before raising quality even once. In practice there's always some
ordinary jitter -- if even 1 picture in every 8 or 9 goes slightly
over budget (completely normal, not a real problem), the count got
reset to zero right before it would have paid off. Quality could get
stuck low indefinitely even on a perfectly fine connection, which is
what showed up in testing as "it doesn't increase at all" -- not a
slow climb, but a climb that could never finish.

Looking at "what fraction of the last 15 were fine" instead of "were
ALL of the last 10 fine" means a little jitter can no longer block
recovery forever. The same idea already exists elsewhere in this file
for other numbers (rtt/net/server), which use a rolling average rather
than a single raw sample for exactly this reason.


ON-SCREEN TRANSPARENCY
-------------------------
The debug HUD shows current send quality next to the target fps, so
a lower quality number always has a visible reason instead of looking
like an unexplained drop. If fps is still below target even at the
current quality, a note explains that the uplink can't keep up right
now -- that's the floor doing its job, not a bug.


OPEN QUESTION, NOT YET AN ISSUE
-----------------------------------
Quality decreases happen on the very first miss. If that also turns
out to be too jumpy in practice (reacting to single harmless blips the
same way the old streak-based increase did), the same window-based
tolerance used for the increase side could be applied to the decrease
side too. Not changed yet because nothing observed so far suggests
it's a problem -- fast reaction to a real slowdown is the point, and
changing this without a reason to would be guessing.
